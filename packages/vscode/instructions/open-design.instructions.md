---
name: OpenDesign
description: Guidance for using the OpenDesign tools to generate design artifacts (landing pages, decks, prototypes, dashboards) directly in this workspace.
---

OpenDesign is a bundled catalog of design skills and design templates (reusable task recipes and rendering styles — both usable interchangeably as a `skillId`) plus design systems (brand-inspired visual token sets) that help you produce a polished design artifact — an HTML page, a slide deck, a dashboard, a component — for the user, generated directly into their open workspace.

Every skill/template id is namespaced as `od:<mode>:<name>` (e.g. `od:deck:guizang-ppt`), where `mode` is one of: `prototype`, `deck`, `design-system`, `image`, `video`, `template`, `utility`, `audio`. Always pass the full namespaced id as `skillId`. Note: mode `design-system` means "a skill that helps author a design-system deliverable" — it has nothing to do with `designSystemId`, which selects from the separate library of ~150 prebuilt brand design systems (see step 2).

Reach for these tools whenever the user asks you to design, build, mock up, or generate something visual: a landing page, a pitch deck, a dashboard, a prototype, a marketing page, or similar. You do not need the user to say "OpenDesign" explicitly.

A small, curated subset of skills/templates also has its own `/`-invocable slash command (e.g. `/guizang-ppt`) — if the user's request closely matches one of those, prefer it; it pins the exact skillId and often a ready-made example brief, removing any guesswork.

All OpenDesign content (skill/template text, design system tokens, example briefs) is delivered to you as plain text through the tool calls below — never as a file path. You never need to, and should not, browse, search, or read any files outside the current workspace (including this extension's own installation directory) to find OpenDesign content; if a tool result happens to mention a file name from OpenDesign's own internal layout, treat it as descriptive text only, not something to go open.

Follow this flow. **Do not search the filesystem, workspace, or this extension's own installation directory to "find the template" or "understand the expected structure" first — `list_open_design_skills` and `prepare_open_design_brief` already return everything you need as plain text; a file search is never the right first step here.**

1. Call `list_open_design_skills` (optionally with a `query` and/or an exact `mode`) to find a skill or design template that matches what the user wants. Pick the best match by name/description/triggers, and prefer a result's `examplePrompt` (adapted to the user's specifics) over inventing your own brief when one is present and closely fits.
2. There is an **active design system**, persisted per workspace (`openDesign.activeDesignSystemId` setting), shown in the status bar. If the user mentions a brand, company, industry, or visual style that differs from what's active, call `list_open_design_design_systems` (optionally with a `query` and/or an exact `category` — call with no arguments first to see categories, and check each result's `active` flag) to find the right one, and pass its id explicitly to `prepare_open_design_brief` — doing so also makes it the new active one going forward, so you don't need to re-specify it on later requests in the same session. If the user hasn't mentioned any direction, just omit `designSystemId` from `prepare_open_design_brief` and it will silently use whatever is currently active (or none). Only call `set_active_design_system` directly when the user wants to pin a look before generating anything ("let's use the Starbucks look from now on"). The user can also run the "OpenDesign: Browse Design Systems" command from the Command Palette (or click the status bar item) to pick one via a fuzzy-searchable, category-grouped picker, which sets it as active immediately.
3. Call `prepare_open_design_brief` with the chosen `skillId`, optional `designSystemId` (per step 2), and the user's `brief` (their request, in their own words). This returns `instructions` to follow, a `suggestedEntryPath`, and the `designSystemId`/`designSystemName` actually used (whether explicit or defaulted from active) — mention which one it was if it wasn't obvious from the conversation. It does NOT write any files.
4. Follow the returned `instructions` and author the artifact's entry file (plus any supporting files) yourself, using your own file-editing tools. Do not look for a separate tool to write the design content.
5. Call `register_open_design_artifact` with the entry path, a `kind`, a `title`, and any `supportingFiles`, so the artifact is recognized and gets its manifest sidecar written.
6. Optionally call `get_open_design_artifact` to confirm what was written before telling the user it's done — its `openComments` field lists any pending feedback left in the preview editor that you should address before finishing.

Generated artifacts live under the workspace's configured OpenDesign output directory (default `.open-design/`) so they stay visible in the file explorer and are trackable in version control like any other project file. Once an HTML artifact is registered, it opens automatically in the **OpenDesign Artifact Preview** editor (also reachable via the "OpenDesign: Open Artifact Preview" command or right-click on any `.html` file) — a live rendering with View/Comment/Edit modes. In Comment mode the user can pin notes on specific elements and send them into a new chat message; in Edit mode they can directly tweak text/color/size on HTML artifacts. Neither mode writes files through you — comments and edits are applied through the editor itself. **Never open the artifact yourself** (e.g. via Simple Browser, a `file://` URL, or any other browser/preview tool) to show the result — the automatic preview above is the only correct way; opening a `file://` URL directly will be blocked by VS Code as an untrusted local file and confuse the user.

If the user wants to start from or riff on an existing example rather than build something new, prefer `remix_open_design_example` (skillId must have a non-empty `exampleArtifactPath`) over `prepare_open_design_brief` — it copies a working starting artifact into the workspace and tells you to modify it rather than regenerate from scratch. The user can also run "OpenDesign: Browse Gallery" from the Command Palette to pick and remix an example directly, without going through chat first.

If the user wants a brand/style that isn't one of the ~150 bundled design systems ("use our own brand colors", "match our website", "set up a custom design system for..."), call `create_open_design_design_system` with a `name`, a `brief` describing the brand, and an optional `sourceUrl` if they gave you a website to match. It returns `instructions` for writing a new `DESIGN.md` yourself (same file shape as every bundled design system) plus, when a `sourceUrl` was given, a best-effort extracted starting palette/font list to incorporate — treat that as a rough starting point, not ground truth. It does NOT write any files. After writing the file, call `set_active_design_system` with the returned `id` — there's no separate "register" step for design systems; a written `DESIGN.md` is immediately selectable, the same way generated artifacts are immediately visible once written.

If the user wants an already-*existing* design system imported exactly (they already have a real one — Figma tokens, a repo's `tailwind.config`, an existing `DESIGN.md`) rather than one invented from a brief, point them at the "OpenDesign: Import Design System" command (Command Palette, or the leading item in "OpenDesign: Browse Design Systems") instead — it writes the file deterministically from a file/paste/GitHub source, with no model involved, so nothing gets paraphrased.

Once the user is happy with a generated or refined artifact and wants it turned into real, working code in this app ("turn this into a real component", "add this to the app", "wire this into my codebase"), call `port_open_design_artifact_to_app` with the artifact's `entryPath`. It returns `instructions` for reproducing the artifact's design as idiomatic code in this workspace's actual application — read the returned instructions carefully: they'll tell you to find and follow a real existing component in this codebase as your pattern reference (its styling approach, conventions, file organization) rather than copying the artifact's HTML/CSS verbatim, and to leave routing/navigation wiring as a separate step for the user. It does NOT write any files itself. This is also reachable via a "Promote to App Code" button in the Artifact Preview editor's toolbar, which prefills a chat message naming the tool and artifact for you.
