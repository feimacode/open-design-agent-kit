---
name: Open Design
description: Guidance for using the Open Design tools to generate design artifacts (landing pages, decks, prototypes, dashboards) directly in this workspace.
---

Open Design is a bundled catalog of design skills and design templates (reusable task recipes and rendering styles — both usable interchangeably as a `skillId`) plus design systems (brand-inspired visual token sets) that help you produce a polished design artifact — an HTML page, a slide deck, a dashboard, a component — for the user, generated directly into their open workspace.

Every skill/template id is namespaced as `od:<mode>:<name>` (e.g. `od:deck:guizang-ppt`), where `mode` is one of: `prototype`, `deck`, `design-system`, `image`, `video`, `template`, `utility`, `audio`. Always pass the full namespaced id as `skillId`. Note: mode `design-system` means "a skill that helps author a design-system deliverable" — it has nothing to do with `designSystemId`, which selects from the separate library of ~200 prebuilt brand design systems (see step 2).

Reach for these tools whenever the user asks you to design, build, mock up, or generate something visual: a landing page, a pitch deck, a dashboard, a prototype, a marketing page, or similar. You do not need the user to say "Open Design" explicitly.

A small, curated subset of skills/templates also has its own `/`-invocable slash command (e.g. `/guizang-ppt`) — if the user's request closely matches one of those, prefer it; it pins the exact skillId and often a ready-made example brief, removing any guesswork.

All Open Design content (skill/template text, design system tokens, example briefs) is delivered to you as plain text through the tool calls below — never as a file path. You never need to, and should not, browse, search, or read any files outside the current workspace (including this extension's own installation directory) to find Open Design content; if a tool result happens to mention a file name from Open Design's own internal layout, treat it as descriptive text only, not something to go open. **This is true even when `list_open_design_skills`/`list_open_design_design_systems` returns few or no results for your query** — there is no `content.json`, index, schema file, or any other single file anywhere containing this catalog for you to find by searching or grepping; the catalog exists only inside the tool itself. The correct response to an empty/unhelpful result is to call the same tool again with a broader or empty query (or an exact category — call with no arguments first to see which categories exist), never to go looking for the underlying data on disk. **This holds even if you have a terminal or shell tool available in this session** — never run `ls`, `find`, `grep`, `cat`, or any other command to explore, list, or read Open Design's skills, design systems, or any related content or files, on any path, inside or outside the workspace. Having shell access does not make that the right tool here; the `list_open_design_*`/`prepare_open_design_brief` tools are the only correct way to discover or read this content, regardless of what other general-purpose tools happen to be available to you.

<!-- voice:start -->
**How to talk to the user.** Many people using Open Design don't write code, so:
- Use the user's own words. If they say "artifact", "design tokens" or give a file path, use those terms back; otherwise use the plain words below.
- Keep the machinery out of replies: no tool names, no ids like `od:prototype:poster-hero`, no internal files (`.artifact.json`, `.comments.json`, `config.json`), and not the words "register", "manifest", "sidecar", "entry" or "surface", unless the user used them first.
- Explain a print term the first time it comes up, in one short clause, and not again.
- Say where a file is the way the user would find it ("in your Open Design folder, under seed-swap-flyer"). Give a raw path only where the user can click it (Claude Code, Claude Desktop's Code tab, VS Code) or asks for it.
- End each reply that finishes a step with one line on what they can do next, with at most two options ("Want it in Instagram sizes too, or is it ready to print?").

| Instead of | Say |
|---|---|
| artifact, entry, registered | your design, saved |
| design system, active design system | your style (the first time: "a saved style: colours, fonts and spacing") |
| surface, skill, template, recipe | kind of design, starting layout, or nothing |
| workspace, output directory | your folder, your Open Design folder |
| bleed | print edge ("a few millimetres extra that the printer trims off") |
| trim size | final size |
| preflight findings, errors | "I checked it and fixed…", "one thing to look at:" |
| export | save as PDF, save as an image |
| inline preview, MCP App | the preview above |

Follow this flow. **Do not search the filesystem, workspace, or this extension's own installation directory to "find the template" or "understand the expected structure" first — `list_open_design_skills` and `prepare_open_design_brief` already return everything you need as plain text; a file search is never the right first step here.**

1. Call `list_open_design_skills` (optionally with a `query` and/or an exact `mode`) to find a skill or design template that matches what the user wants. Pick the best match by name/description/triggers, and prefer a result's `examplePrompt` (adapted to the user's specifics) over inventing your own brief when one is present and closely fits.
2. There is an **active design system**, persisted per workspace (`openDesign.activeDesignSystemId` setting), shown in the status bar. If the user mentions a brand, company, industry, or visual style that differs from what's active, call `list_open_design_design_systems` (optionally with a `query` and/or an exact `category` — call with no arguments first to see categories, and check each result's `active` flag) to find the right one, and pass its id explicitly to `prepare_open_design_brief` — doing so also makes it the new active one going forward, so you don't need to re-specify it on later requests in the same session. For **phone screens** (the Mobile app surface, or a brief like "a budgeting app that feels like Monzo"), look in the `Mobile Apps` category first, with the app's name as `query`: those systems are adapted from the real iOS apps (tab bars, sheets, iOS point sizes). Use `<app>-ios` (e.g. `spotify-ios`) for phone screens even when a web system of the same brand exists (`spotify`); the web one stays the right choice for web pages. If the user hasn't mentioned any direction and one is active, just omit `designSystemId` from `prepare_open_design_brief` and it will use the active one. **If none is active and the user hasn't named a direction, recommend one** before preparing a new design (not for an edit, a remix or an export): call `recommend_open_design_design_systems` with what you know from the request, the conversation and the workspace (`industries`, `moods`, `theme`, `surface`, `likeBrands`, `brief`), leaving out what you don't know. If its result has `questions`, ask them once, in one message, as short multiple-choice options, and accept "you pick"; then call it again with the answers. Ask them in the same message as any surface questions, three in total at most. Show the shortlist as a short numbered list with each name and its `reason`. Don't wait for a pick unless you asked questions: go ahead with the first recommendation, pass its id to `prepare_open_design_brief`, and say which one you used and that they can switch (or browse with the "Open Design: Browse Design Systems" command). Only call `set_active_design_system` directly when the user wants to pin a look before generating anything ("let's use the Starbucks look from now on"). The user can also run the "Open Design: Browse Design Systems" command from the Command Palette (or click the status bar item) to pick one via a fuzzy-searchable, category-grouped picker, which sets it as active immediately.
3. Call `prepare_open_design_brief` with the chosen `skillId`, optional `designSystemId` (per step 2), and the user's `brief` (their request, in their own words). This returns `instructions` to follow, a `suggestedEntryPath`, and the `designSystemId`/`designSystemName` actually used (whether explicit or defaulted from active) — mention which one it was if it wasn't obvious from the conversation. It does NOT write any files.
4. Follow the returned `instructions` and author the artifact's entry file (plus any supporting files) yourself, using your own file-editing tools. Do not look for a separate tool to write the design content.
5. Call `register_open_design_artifact` with the entry path, a `kind`, a `title`, and any `supportingFiles`, so the artifact is recognized and gets its manifest sidecar written.
6. Call `check_open_design_artifact` with the entry path before telling the user it's done (after creating an artifact, and again after a substantial edit). It renders the artifact and returns screenshots plus preflight findings: fix every **error**, then look at the screenshots for what the checks can't measure — balance, hierarchy, crowded or empty areas, text over busy imagery — and fix what's clearly wrong. Taste warnings (`slop-glow`, `card-row`, `uniform-surface`, `type-scale`, `intent`) are worth a look: fix them unless the brief or the design system asks for that look, and never add `data-od-allow` only to silence one. Re-check after fixing, but stop after two fix rounds and tell the user about anything left. **Then get a second look** before you call it done: once the checks are clean or the fix rounds are spent, run the `open-design-critique` skill (the `/open-design-critique` prompt in VS Code), which has a fresh critic judge the latest check run against the brief and the design system on purpose and hierarchy, typography, colour and contrast, layout and rhythm, copy, states, and fit, so build with those in mind. One critique round: on `polish`, apply its fixes once, register and re-check, then report done without another critique; on `rework`, tell the user what's wrong and ask before rebuilding; on `ship`, it's done. The brief or design system wins over a finding against a look it asks for, and the user can ask for another opinion at any time or say they don't want one. **3D designs are the exception:** when the check returns a 3D review sheet, a clean check isn't the end. Get the critique the check result asks for (the `3d-object` skill's scorecard, from a subagent where your host has one), then fix, re-check and re-critique for up to three critique rounds, which replace the two-fix-round limit and the second look above. Don't describe the screenshots to the user unless they ask. If it returns `no-browser`, skip checking and tell the user once that visual checks need Chrome, Edge or Chromium installed.
7. Optionally call `get_open_design_artifact` to confirm what was written before telling the user it's done — its `openComments` field lists any pending feedback left in the preview editor that you should address before finishing.

When a request names a **kind of thing to make** (a prototype or landing page, mobile app, slides, document, wireframe, animation, résumé, research synthesis, data report, poster or flier, social post, diagram, 3D object), call `list_open_design_skills` with `surface` set to that kind first (`surface: "list"` shows the ids). Pick from its entries and follow the surface's prompt when it names one. **Questions:** a surface lists a few `questions`, each with `options`, a `default` and what the answer `changes`. Ask only the ones the request, the conversation and the workspace don't already answer: at most three in total, merged with any design-system recommender questions (surface ones first), in one message, as multiple choice, accepting "you pick" (then use the question's `default`). A request that already says enough gets no questions. Pass the answers to `prepare_open_design_brief` as `answers` (question id to answer) and what you decided without asking as `assumptions` (up to six short lines), then pass both, with the request in one line as `text`, to `register_open_design_artifact` as `brief`. When the design is ready, list the assumptions in one sentence and invite a change ("I assumed a dark theme and one sign-up button; say if you want otherwise"). A request for one specific template or style still goes straight to it. Never pick an entry marked `stub: true`: it only advertises an upstream skill and has no instructions here.

For **engineering documents** (an RFC, ADR, postmortem, PR explainer or changelog page), use the matching skill (`od:prototype:rfc`, `adr`, `postmortem`, `pr-explainer`, `changelog-page`). Gather the facts yourself first, from git (`git log`, `git diff`, `gh pr view` when available) and the files involved, and register what you read as `sources`. Never invent incident facts, dates or numbers: ask for them. To turn a **folder of Markdown docs** into pages, follow the docs flow (the `/open-design-docs` command): one page per file, one template for the set, and on a re-run only the pages whose Markdown changed.

For a **recurring design** ("every week", "on a schedule"), follow the recurring flow (the `/open-design-recurring` command): it writes the job file in `.open-design/jobs/`, but scheduled runs need Claude Code or Claude Desktop with the Open Design MCP server, since VS Code has no scheduler.

If the request is **based on a document** (it names or attaches a report, spec, spreadsheet, PDF or existing deck, or points at repository files such as `CHANGELOG.md`, `docs/adr/`, an RFC or a metrics CSV), generate from it rather than from memory: pass those workspace paths as `sources` to `prepare_open_design_brief`. Typical examples: "a release deck from CHANGELOG.md", "an architecture review from docs/adr/", "a board update from metrics/q3.xlsx", "turn docs/q3-report.docx into a pitch". The tool extracts each document (DOCX, PPTX, XLSX, PDF with `pdftotext`, Markdown, text, CSV) to Markdown and returns instructions that make you **write an outline first and stop for the user's approval** before building. Follow them: read the extracted text by line range, write `outline.md`, show it, and wait (unless the user said to just build it). Then register with the same `sources`; its result lists numbers on the page that it couldn't find in the sources, so check and fix each one. Use `read_open_design_source` on its own to look inside a document before deciding how to use it. For a whole folder of files (such as `docs/adr/`), pass the relevant files individually (up to 10).

When the user wants to **choose colors and fonts**, a palette or a type pairing, or a look for a new brand ("show me some color and type options", "what could our brand look like?"), run the exploration with the style-tile skill (`skillId: "od:design-system:style-tile"`): it makes compact tiles (palette with contrast, type specimen, components) instead of pages, 4 by default. To vary the active design system rather than replace it ("the same but warmer"), use `axis: "custom"` with one direction per variation. When the user picks a tile, call `choose_open_design_direction` with `next: "save-design-system"`: the tile's tokens are copied verbatim into the new system, which then becomes active.

If the user explicitly asks for **options to compare** ("show me three directions for…", "a few different versions of…", "explore some alternatives", "I'm not sure what style I want, show me options"), run a **design exploration** instead of steps 3–5. Don't explore for an ordinary request ("design a pricing page"): it costs several generations.
1. Call `prepare_open_design_exploration` with the `skillId` and the user's `brief` (and `count` 2–4 if they gave a number; default 3). The tool picks deliberately different directions itself: visual styles when no design system is active, layout/narrative structures when one is (so the brand is kept), or pass `axis: "custom"` with `customDirections` when the user named what should vary ("three hero concepts"). Pass `directionIds` only when the brief's tone clearly calls for specific ones (e.g. `editorial-monocle` for a magazine, `brutalist-experimental` for an art or agency site). If the result says the active design system was set aside, tell the user.
2. For each returned direction, follow `sharedInstructions` followed by that direction's own `instructions`, write its file at its `suggestedEntryPath`, and call `register_open_design_artifact` with the `explorationId` and that direction's `directionId`. Directions are quick **sketches** (one screen, or a cover plus two slides), not full builds. If you can delegate work to sub-agents, generate the directions in parallel, passing each one `sharedInstructions` plus its own `instructions`.
3. Call `compare_open_design_exploration` with `contactSheet: true`. If you can view images, open the contact sheet and check the directions really look different (layout and hero pattern, not just colour); regenerate any that resembles another.
4. Tell the user the directions are ready. Each one opens in the Artifact Preview, whose Prev/Next buttons step through the directions; the exploration is also listed in the Open Design **Collections** view, whose "Open comparison in browser" entry opens the side-by-side comparison page in their own browser. Don't open it in Simple Browser or via a file:// URL; VS Code blocks that. Ask which direction to take forward.
5. When the user picks one, call `choose_open_design_direction` with `next`: `build-out` (build the chosen sketch out at full fidelity), `merge` (the same, taking named aspects from other directions via `mergeFrom`, e.g. "B with A's hero"), or `save-design-system` (turn the direction into a reusable custom design system). Follow the returned `instructions` and register the result as they say.

Generated artifacts live under the workspace's configured Open Design output directory (default `.open-design/`) so they stay visible in the file explorer and are trackable in version control like any other project file. Once an HTML artifact is registered, it opens automatically in the **Open Design Artifact Preview** editor (also reachable via the "Open Design: Open Artifact Preview" command or right-click on any `.html` file) — a live rendering with View/Comment/Edit modes. In Comment mode the user can pin notes on specific elements and send them into a new chat message; in Edit mode they can directly tweak text/color/size on HTML artifacts. Neither mode writes files through you — comments and edits are applied through the editor itself. **Never open the artifact yourself** (e.g. via Simple Browser, a `file://` URL, or any other browser/preview tool) to show the result — the automatic preview above is the only correct way; opening a `file://` URL directly will be blocked by VS Code as an untrusted local file and confuse the user.

If the user wants to start from or riff on an existing example rather than build something new, prefer `remix_open_design_example` (skillId must be an entry with `remixable: true`) over `prepare_open_design_brief` — it copies a working starting artifact into the workspace and tells you to modify it rather than regenerate from scratch. The user can also run "Open Design: Browse Gallery" from the Command Palette to pick and remix an example directly, without going through chat first.

If the user wants a brand/style that isn't one of the ~200 bundled design systems ("use our own brand colors", "match our website", "set up a custom design system for..."), call `create_open_design_design_system` with a `name`, a `brief` describing the brand, and an optional `sourceUrl` if they gave you a website to match. It returns `instructions` for writing a new `DESIGN.md` yourself (same file shape as every bundled design system) plus, when a `sourceUrl` was given, a best-effort extracted starting palette/font list to incorporate — treat that as a rough starting point, not ground truth. It does NOT write any files. After writing the file, call `set_active_design_system` with the returned `id` — there's no separate "register" step for design systems; a written `DESIGN.md` is immediately selectable, the same way generated artifacts are immediately visible once written.

If the user wants an already-*existing* design system imported exactly (they already have a real one — Figma tokens, a repo's `tailwind.config`, an existing `DESIGN.md`) rather than one invented from a brief, point them at the "Open Design: Import Design System" command (Command Palette, or the leading item in "Open Design: Browse Design Systems") instead — it writes the file deterministically from a file/paste/GitHub source, with no model involved, so nothing gets paraphrased.

Once the user is happy with a generated or refined artifact and wants it turned into real, working code in this app ("turn this into a real component", "add this to the app", "wire this into my codebase"), call `port_open_design_artifact_to_app` with the artifact's `entryPath`. It returns `instructions` for reproducing the artifact's design as idiomatic code in this workspace's actual application — read the returned instructions carefully: they'll tell you to find and follow a real existing component in this codebase as your pattern reference (its styling approach, conventions, file organization) rather than copying the artifact's HTML/CSS verbatim, and to leave routing/navigation wiring as a separate step for the user. It does NOT write any files itself. This is also reachable via a "Promote to App Code" button in the Artifact Preview editor's toolbar, which prefills a chat message naming the tool and artifact for you.

**Working with Impeccable.** After porting, if a skill named `impeccable` is in your own skill list, end your reply with one suggestion: run `/impeccable polish` (or `/impeccable audit`) on the component you just wrote. Say nothing about Impeccable when you don't have that skill. In a code project, once you've set a design system there and the project has no `DESIGN.md`, you may offer once to save it as the project's `DESIGN.md` so other tools can read it; when the user agrees, call `set_active_design_system` again with `writeProjectDesignMd: true` (it never overwrites an existing file).

When the user wants reusable components rather than one page in the app ("make Material 3 components for my React app from this", "a component library from this design", "an MUI / shadcn set for these screens"), call `prepare_open_design_component_library` instead, with the artifact's `entryPaths` (or the `collectionId` for every screen) and `library` `mui`, `shadcn` or `auto`. Follow its stages in order: write the `components.md` inventory and **stop for the user's yes** before any code, use the generated theme as is, wrap the library's own components, add the gallery, run the app's type check, then call the tool again with `record`. It writes no app code itself. "Material 3" means `mui`. The same toolbar button offers "A component set", which prefills a request for this tool.

When the artifact is meant to be posted or uploaded as an image (an X/Twitter post, Instagram or LinkedIn image, Xiaohongshu cards, a YouTube thumbnail, a poster), call `export_open_design_artifact` with its `entryPath` after registering it. It renders the artifact in a headless browser and writes PNG/JPEG file(s) under the artifact's own `exports/` folder, sized from the source skill automatically unless you pass `width`/`height`. For multi-card designs, give each card a `data-od-card` attribute and pass `selector: "[data-od-card]"` to get one numbered image per card. Pass `maxBytes` with the platform's upload limit (X 5000000, YouTube thumbnail 2000000, Instagram 8000000). Tell the user the exported file paths. For a social-post request where the platform or format isn't clear, ask the user which platform it's for before generating (X, Instagram, LinkedIn, Xiaohongshu, Stories/Reels, a YouTube thumbnail or video), and mention that the `/open-design-social-post` command walks through the whole flow with the right sizes for each platform. Animated designs (motion frames, title cards, animated charts, sprite or WebGL animations) export as video or GIF: call `export_open_design_artifact` with `format: "mp4"`, `"webm"` or `"gif"`. Time runs on a virtual clock, so the frames are exact and the same on every run; the length comes from the page (`data-duration` frames or the longest animation) unless you pass `duration`. Before exporting, call `check_open_design_artifact` with `at` (e.g. `[0, 1.5, 3]`) to see the start, middle and end. Export needs an installed ffmpeg: if it reports `no-ffmpeg` or `ffmpeg-missing-encoder`, tell the user what to install rather than trying another way. Compositions built with the HyperFrames framework are the exception: the brief's own instructions render them with the HyperFrames CLI. After registering a slide deck, offer to export it as PowerPoint or PDF, and when the user wants that, call `export_open_design_artifact` with `format: "pptx"` or `"pdf"` (one full-bleed image per slide; not editable text). `format: "pdf"` on an ordinary page prints it as a vector PDF.

For a **diagram** of a system — architecture, dependencies, a request flow, a database schema (ERD), a state machine or a sequence of calls ("diagram how our services talk", "draw the schema", "how does checkout work?") — use the `diagram` skill (`od:prototype:diagram`, or remix its example `od:prototype:diagram:example`). Read the relevant code first and draw only what you read. Write nodes with `data-rank`/`data-lane` and hidden links, never coordinates, then call `add_open_design_diagram_runtime` (it inserts the layout runtime; never write that script yourself), register with kind `diagram` and the files you read as `sources`, and check it. When a later check or `get_open_design_artifact` reports that its sources changed, offer to redraw it.

For a **3D object** — a product shot, a 3D logo, a turntable, or the user's own `.glb`/`.gltf` model ("make a 3D render of our bottle", "turn the logo into 3D", "a product shot of models/headphones.glb") — use the `3d-object` skill (`od:prototype:3d-object`). It's one three.js scene with studio lighting, materials from the design system's tokens, a ground shadow and a turntable. Load three.js exactly as the skill says (its import map for the pinned `three@0.160.0` module build): older `three.min.js` and `examples/js` script tags no longer exist and leave the page blank. Copy a user's model under `assets/` next to the design and load it with `GLTFLoader`, framing the camera from its bounding box. The page must expose `window.odScene` (`ready`, resolved after a direct render once everything has loaded, and `rotate`); exports and checks turn on software WebGL and wait for it. Fix `webgl` findings before exporting. For a cut-out to place on slides or pages, export `format: "png"` with `transparent: true` from a scene with no background; for a turntable, `format: "mp4"` or `"gif"` with `duration` equal to one rotation.

For an **HTML email** (newsletter, launch or product-update email), use the `email-campaign` skill: it builds a table-based, inbox-safe email marked `data-od-email`. Check it, then export with `export_open_design_artifact` and `format: "email"` (add `baseUrl` once the user has hosted the `assets/` folder, so image URLs become absolute), and tell the user to send themselves a test before sending to a list. When the user wants a design **pasted into another editor** (a WeChat Official Account article, a Notion page, a newsletter tool), export with `format: "paste"` and `target` `wechat`, `notion`, `newsletter` or `generic`; styles are inlined from what the browser rendered. To use either file, the user opens it in a browser, selects all and copies. In VS Code the preview's **Export → Copy for** menu does the copying in one step.

For a **campaign** (one message across several channels or sizes, ad banners in several sizes, or the same creative in several languages), follow the campaign flow (the `/open-design-campaign` command walks through it): agree a copy deck saved as a CSV, build one fluid master bound to it with `data-od-field` (headline and subhead marked `data-od-fit` for long translations), check every chosen shape per row, and export with `presets`, `data` and `campaignSheet: true`.

For a **poster, flyer or other print piece**, or when the user wants a design in other sizes, follow the poster flow (and mention the `/open-design-poster` command, which walks through it): ask whether it's for print or screens and which size if the brief doesn't say, then pass that canvas `format` (e.g. `a3`, `a2`, `ig-portrait`, `story`) with `fluid: true` to `prepare_open_design_brief`, and the same `format` to `register_open_design_artifact`. A fluid poster reflows to any shape, so the size can change later without regenerating. Use `create_open_design_qr_code` for any QR code (never draw a fake one). Before exporting, call `check_open_design_artifact` and fix every preflight error (use `export_open_design_artifact` with `checkOnly: true` for checks with `data` rows or `shapeSheet`). Export with `preset` set to the format id: print formats give a print-ready PDF with bleed (add `cropMarks: true` if asked). For other sizes, export with `presets` (several shapes at once) and show a shape sheet (`shapeSheet: true, checkOnly: true`); for a shape that looks wrong, `adapt_open_design_artifact` returns instructions to tune it in the same file. In the preview, the Shape dropdown shows the poster at any size. For one poster, card or certificate per person or row, mark the changing text with `data-od-field="<column>"` and export with `data` set to the user's CSV/XLSX/JSON file. Tell the user print PDFs are RGB.

When the user wants to **share** a design with people who don't have this project open: for a link ("publish this", "deploy it", "give me a link to send the team", "host it somewhere"), call `publish_open_design_artifact` with its `entryPath` (pass `provider` only if they already said where; otherwise it returns the choices to show them). It builds a deploy-ready folder and returns step-by-step instructions to run with your terminal under the user's own CLI login, or as a temporary no-account link. Follow them exactly: they stop for the user's explicit yes before anything goes online, and after a successful deploy you call the tool again with `published` to record the link. For a single file to attach or send ("export it as one HTML file"), call `export_open_design_artifact` with `format: "standalone"` instead; nothing goes online. The `/open-design-publish` command walks through the whole flow, and the artifact preview's **Share** button offers the same choices.

If the user wants to pull a design directly from Figma ("build this Figma frame", "implement this Figma design", "turn this Figma link into code"), call `pull_open_design_figma_frame` with `figmaUrl` (a frame-scoped link from Figma's "Copy link to selection", not a bare file link) and an optional `designSystemId`, then follow its instructions: they use the user's Figma connection when there is one (no token needed), and a Figma access token otherwise.

If the user wants to push a finished artifact INTO Figma as editable layers ("get this into Figma", "hand this off to design", "push this to Figma"), call `push_open_design_artifact_to_figma` with its `entryPath` and follow its instructions: with the user's Figma connection you build the layers yourself after they choose an existing file or a new one; without it, they fall back to the "OD Figma Import" plugin. The preview toolbar's **Export → Figma** leads to the same tool.

If the user wants a **design collection** — several connected, individually-real screens generated together as one flow ("a 4-screen onboarding flow", "generate the main screens of this app", "wireframe a user flow" at real/high fidelity rather than a single flattened board) — there is no dedicated "start collection" tool; you drive it yourself as a loop over the existing tools:
1. Decide the screen list from the brief yourself (how many screens, what each one's role is) — the same judgment call the `wireframe-mobile-flow` skill already makes for its low-fidelity board, just applied to real separate screens here.
2. Derive a `collectionId` once — a short slug of the collection's name (e.g. "Fintech Onboarding Flow" → `fintech-onboarding-flow`) — and a `collectionName`. Reuse both verbatim on every call below; do not regenerate or vary them per screen.
3. For each screen, call `prepare_open_design_brief` with that screen's own `brief`, plus `collectionId`, `collectionName`, and a short `screenRole` (e.g. "splash", "home", "detail", "checkout") — pass `screenTotal` too if you know the final count, for an accurate "screen N of M" framing. Pass `designSystemId` explicitly only on the **first** screen; it stays active and is reused automatically on the rest, so all screens share one visual system without you re-specifying it. The returned instructions already include what the other screens in this collection are (role + title), composed automatically from what's already registered — you don't need to track or repeat that yourself.
4. Author each screen's file, then call `register_open_design_artifact` with the same `collectionId`/`collectionName`, a 0-based `screenIndex`, and the same `screenRole` used in step 3.
5. Repeat 3-4 for each remaining screen. Once done, mention the new "Open Design Collections" view (activity bar) where the user can browse and open every screen, and that each screen's Artifact Preview editor gets Prev/Next buttons to move between siblings in the flow.

When a step would **hand work to another service** (import into Canva, read or push a Figma frame, save to Google Drive, write a Notion page, share in Slack, or post to a social network), call `list_open_design_integrations` first with the `capability` (plus `platform` for a social post). Then:
1. Check your own tools for one matching the returned patterns, including deferred or on-demand tools you can search for. If one is there, use it, calling its tools by their server-defined names (e.g. Canva's `import-design-from-url`).
2. If none is, offer to set up the first provider, once per conversation and only when the step needs it: say what it does and what sign-in it needs. Only after the user says yes, follow the returned setup steps (user-level configuration only). Never install silently, and never ask for an API key or write one into a file: the user sets it themselves.
3. Help the user sign in and reload if needed, then confirm by listing your tools.
4. If the user declines or setup fails, carry on with the workflow's manual path.

Anything that publishes, sends or posts on the user's account still needs their go-ahead first.
