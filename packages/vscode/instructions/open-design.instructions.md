---
name: Open Design
description: Guidance for using the Open Design tools to generate design artifacts (landing pages, decks, prototypes, dashboards) directly in this workspace.
---

Open Design is a bundled catalog of design skills and design templates (reusable task recipes and rendering styles — both usable interchangeably as a `skillId`) plus design systems (brand-inspired visual token sets) that help you produce a polished design artifact — an HTML page, a slide deck, a dashboard, a component — for the user, generated directly into their open workspace.

Every skill/template id is namespaced as `od:<mode>:<name>` (e.g. `od:deck:guizang-ppt`), where `mode` is one of: `prototype`, `deck`, `design-system`, `image`, `video`, `template`, `utility`, `audio`. Always pass the full namespaced id as `skillId`. Note: mode `design-system` means "a skill that helps author a design-system deliverable" — it has nothing to do with `designSystemId`, which selects from the separate library of ~150 prebuilt brand design systems (see step 2).

Reach for these tools whenever the user asks you to design, build, mock up, or generate something visual: a landing page, a pitch deck, a dashboard, a prototype, a marketing page, or similar. You do not need the user to say "Open Design" explicitly.

A small, curated subset of skills/templates also has its own `/`-invocable slash command (e.g. `/guizang-ppt`) — if the user's request closely matches one of those, prefer it; it pins the exact skillId and often a ready-made example brief, removing any guesswork.

All Open Design content (skill/template text, design system tokens, example briefs) is delivered to you as plain text through the tool calls below — never as a file path. You never need to, and should not, browse, search, or read any files outside the current workspace (including this extension's own installation directory) to find Open Design content; if a tool result happens to mention a file name from Open Design's own internal layout, treat it as descriptive text only, not something to go open. **This is true even when `list_open_design_skills`/`list_open_design_design_systems` returns few or no results for your query** — there is no `content.json`, index, schema file, or any other single file anywhere containing this catalog for you to find by searching or grepping; the catalog exists only inside the tool itself. The correct response to an empty/unhelpful result is to call the same tool again with a broader or empty query (or an exact category — call with no arguments first to see which categories exist), never to go looking for the underlying data on disk. **This holds even if you have a terminal or shell tool available in this session** — never run `ls`, `find`, `grep`, `cat`, or any other command to explore, list, or read Open Design's skills, design systems, or any related content or files, on any path, inside or outside the workspace. Having shell access does not make that the right tool here; the `list_open_design_*`/`prepare_open_design_brief` tools are the only correct way to discover or read this content, regardless of what other general-purpose tools happen to be available to you.

Follow this flow. **Do not search the filesystem, workspace, or this extension's own installation directory to "find the template" or "understand the expected structure" first — `list_open_design_skills` and `prepare_open_design_brief` already return everything you need as plain text; a file search is never the right first step here.**

1. Call `list_open_design_skills` (optionally with a `query` and/or an exact `mode`) to find a skill or design template that matches what the user wants. Pick the best match by name/description/triggers, and prefer a result's `examplePrompt` (adapted to the user's specifics) over inventing your own brief when one is present and closely fits.
2. There is an **active design system**, persisted per workspace (`openDesign.activeDesignSystemId` setting), shown in the status bar. If the user mentions a brand, company, industry, or visual style that differs from what's active, call `list_open_design_design_systems` (optionally with a `query` and/or an exact `category` — call with no arguments first to see categories, and check each result's `active` flag) to find the right one, and pass its id explicitly to `prepare_open_design_brief` — doing so also makes it the new active one going forward, so you don't need to re-specify it on later requests in the same session. If the user hasn't mentioned any direction, just omit `designSystemId` from `prepare_open_design_brief` and it will silently use whatever is currently active (or none). Only call `set_active_design_system` directly when the user wants to pin a look before generating anything ("let's use the Starbucks look from now on"). The user can also run the "Open Design: Browse Design Systems" command from the Command Palette (or click the status bar item) to pick one via a fuzzy-searchable, category-grouped picker, which sets it as active immediately.
3. Call `prepare_open_design_brief` with the chosen `skillId`, optional `designSystemId` (per step 2), and the user's `brief` (their request, in their own words). This returns `instructions` to follow, a `suggestedEntryPath`, and the `designSystemId`/`designSystemName` actually used (whether explicit or defaulted from active) — mention which one it was if it wasn't obvious from the conversation. It does NOT write any files.
4. Follow the returned `instructions` and author the artifact's entry file (plus any supporting files) yourself, using your own file-editing tools. Do not look for a separate tool to write the design content.
5. Call `register_open_design_artifact` with the entry path, a `kind`, a `title`, and any `supportingFiles`, so the artifact is recognized and gets its manifest sidecar written.
6. Optionally call `get_open_design_artifact` to confirm what was written before telling the user it's done — its `openComments` field lists any pending feedback left in the preview editor that you should address before finishing.

Generated artifacts live under the workspace's configured Open Design output directory (default `.open-design/`) so they stay visible in the file explorer and are trackable in version control like any other project file. Once an HTML artifact is registered, it opens automatically in the **Open Design Artifact Preview** editor (also reachable via the "Open Design: Open Artifact Preview" command or right-click on any `.html` file) — a live rendering with View/Comment/Edit modes. In Comment mode the user can pin notes on specific elements and send them into a new chat message; in Edit mode they can directly tweak text/color/size on HTML artifacts. Neither mode writes files through you — comments and edits are applied through the editor itself. **Never open the artifact yourself** (e.g. via Simple Browser, a `file://` URL, or any other browser/preview tool) to show the result — the automatic preview above is the only correct way; opening a `file://` URL directly will be blocked by VS Code as an untrusted local file and confuse the user.

If the user wants to start from or riff on an existing example rather than build something new, prefer `remix_open_design_example` (skillId must have a non-empty `exampleArtifactPath`) over `prepare_open_design_brief` — it copies a working starting artifact into the workspace and tells you to modify it rather than regenerate from scratch. The user can also run "Open Design: Browse Gallery" from the Command Palette to pick and remix an example directly, without going through chat first.

If the user wants a brand/style that isn't one of the ~150 bundled design systems ("use our own brand colors", "match our website", "set up a custom design system for..."), call `create_open_design_design_system` with a `name`, a `brief` describing the brand, and an optional `sourceUrl` if they gave you a website to match. It returns `instructions` for writing a new `DESIGN.md` yourself (same file shape as every bundled design system) plus, when a `sourceUrl` was given, a best-effort extracted starting palette/font list to incorporate — treat that as a rough starting point, not ground truth. It does NOT write any files. After writing the file, call `set_active_design_system` with the returned `id` — there's no separate "register" step for design systems; a written `DESIGN.md` is immediately selectable, the same way generated artifacts are immediately visible once written.

If the user wants an already-*existing* design system imported exactly (they already have a real one — Figma tokens, a repo's `tailwind.config`, an existing `DESIGN.md`) rather than one invented from a brief, point them at the "Open Design: Import Design System" command (Command Palette, or the leading item in "Open Design: Browse Design Systems") instead — it writes the file deterministically from a file/paste/GitHub source, with no model involved, so nothing gets paraphrased.

Once the user is happy with a generated or refined artifact and wants it turned into real, working code in this app ("turn this into a real component", "add this to the app", "wire this into my codebase"), call `port_open_design_artifact_to_app` with the artifact's `entryPath`. It returns `instructions` for reproducing the artifact's design as idiomatic code in this workspace's actual application — read the returned instructions carefully: they'll tell you to find and follow a real existing component in this codebase as your pattern reference (its styling approach, conventions, file organization) rather than copying the artifact's HTML/CSS verbatim, and to leave routing/navigation wiring as a separate step for the user. It does NOT write any files itself. This is also reachable via a "Promote to App Code" button in the Artifact Preview editor's toolbar, which prefills a chat message naming the tool and artifact for you.

If the user wants to pull a design directly from Figma ("build this Figma frame", "implement this Figma design", "turn this Figma link into code"), call `pull_open_design_figma_frame` with `figmaUrl` (must be a frame-scoped link — Figma's "Copy link to selection", not a bare file link) and an optional `designSystemId`. It requires a Figma personal access token; if none is set, the user needs to run "Open Design: Set Figma Access Token" first (paste a token from Figma → Settings → Personal access tokens — stored encrypted, never shown again). It returns `instructions` embedding a deterministic structural summary of the frame (exact positions/colors/text) as ground truth for a 1:1-fidelity translation, plus a `suggestedEntryPath` — follow the same "author the file yourself, then call `register_open_design_artifact`" pattern as every other generation flow here. It does NOT write any files itself, and it does not import a whole Figma file — only the one linked frame.

If the user wants to push a finished artifact INTO Figma as editable layers ("get this into Figma", "hand this off to design", "push this to Figma"), point them at the "Push to Figma" button in the Artifact Preview editor's toolbar — this is a one-off, semi-manual export (not something you drive through chat): it writes a `<entry>.od-figma.json` capture sidecar next to the artifact, then the user does a one-time "Import plugin from manifest…" step in Figma desktop (the "Open Design: Show Figma Import Plugin Folder" command points at it) to rebuild it as real layers. There is no chat tool for this — don't try to invoke one; just tell the user about the button and, if asked, the one-time plugin setup step.

If the user wants a **design collection** — several connected, individually-real screens generated together as one flow ("a 4-screen onboarding flow", "generate the main screens of this app", "wireframe a user flow" at real/high fidelity rather than a single flattened board) — there is no dedicated "start collection" tool; you drive it yourself as a loop over the existing tools:
1. Decide the screen list from the brief yourself (how many screens, what each one's role is) — the same judgment call the `wireframe-mobile-flow` skill already makes for its low-fidelity board, just applied to real separate screens here.
2. Derive a `collectionId` once — a short slug of the collection's name (e.g. "Fintech Onboarding Flow" → `fintech-onboarding-flow`) — and a `collectionName`. Reuse both verbatim on every call below; do not regenerate or vary them per screen.
3. For each screen, call `prepare_open_design_brief` with that screen's own `brief`, plus `collectionId`, `collectionName`, and a short `screenRole` (e.g. "splash", "home", "detail", "checkout") — pass `screenTotal` too if you know the final count, for an accurate "screen N of M" framing. Pass `designSystemId` explicitly only on the **first** screen; it stays active and is reused automatically on the rest, so all screens share one visual system without you re-specifying it. The returned instructions already include what the other screens in this collection are (role + title), composed automatically from what's already registered — you don't need to track or repeat that yourself.
4. Author each screen's file, then call `register_open_design_artifact` with the same `collectionId`/`collectionName`, a 0-based `screenIndex`, and the same `screenRole` used in step 3.
5. Repeat 3-4 for each remaining screen. Once done, mention the new "Open Design Collections" view (activity bar) where the user can browse and open every screen, and that each screen's Artifact Preview editor gets Prev/Next buttons to move between siblings in the flow.
