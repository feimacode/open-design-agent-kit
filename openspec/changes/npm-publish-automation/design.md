## Context

This session ran a full, real test of the npm-publish path — a local Verdaccio registry, real `npm publish` for `packages/content` → `packages/mcp-server` → `packages/cli` in that order, then a fully isolated fresh-machine `npx` resolution and a real MCP JSON-RPC handshake (`initialize` → `tools/list` → `tools/call`), plus `npx @feimacode/open-design-agent-kit init` from a second fresh scratch project. Everything worked on the first attempt — the earlier `private: true`/`devDependencies` fixes were correct and sufficient. What the exercise exposed instead is that *doing this again for a real release* has no automation at all, unlike the VS Code extension side, which already has a careful two-workflow pipeline (`release.yml` builds and validates on every tag; `publish-marketplace.yml` is separate, manual-only, and gates on a typed `"PUBLISH"` confirmation plus a checksum check against the already-published GitHub Release artifact).

## Goals / Non-Goals

**Goals:**
- Give the three npm packages the same build/validate-then-separately-confirmed-publish shape the VS Code extension already has, not a weaker one.
- Automate the exact regression check this session ran by hand (real publish → fresh-machine resolve → real tool call), since it's the one test that would have caught the original private-package bug.
- Close the small but real correctness gap in `mcp-server`'s dependency range on `content`.
- Fill the two missing READMEs and the missing `engines` fields — cheap, real completeness gaps.

**Non-Goals:**
- Touching `release.yml`/`publish-marketplace.yml` (VS Code side) — already correct, not in scope.
- A general-purpose monorepo release-management overhaul beyond what these three packages need.
- Actually publishing anything for real, or creating an `NPM_TOKEN` secret — that remains a separate, later, explicitly-approved action, same as every other "publish" step this session has deliberately deferred.

## Decisions

### 1. One shared release (extend `release.yml`), not a second parallel pipeline
**Decision (revised after user feedback — the original plan below was wrong):** `release.yml`'s existing `build` job gains additional steps — build `packages/content`, `packages/mcp-server`, `packages/cli`, `npm pack` all three, run the Verdaccio smoke test (Decision 2) as a hard gate — and its `release` job attaches all three `.tgz` files (plus their sha256 checksums, matching the existing `.vsix` treatment) to the *same* GitHub Release as the `.vsix`, under the *same* tag/version. One release, one version, four artifacts, listed on one release page — the VS Code extension and the npm packages can never end up shipped at different, silently-drifted versions from two independent pipelines.

`publish-npm.yml` (new) mirrors `publish-marketplace.yml`'s existing shape exactly: `workflow_dispatch` only, a `confirmation` input that must equal `"PUBLISH"`, `NPM_TOKEN` secret — but instead of rebuilding, it `gh release download`s the three `.tgz` files from that same GitHub Release, verifies their checksums (same as `publish-marketplace.yml` already does for the `.vsix`), and only then runs `npm publish <tarball>` for each, in order: `content`, then `mcp-server`, then `cli`. Publishing the exact, already-checksummed artifact that passed the shared release's checks — not a fresh rebuild that could subtly differ — is the same integrity property `publish-marketplace.yml` already relies on for the `.vsix`; extending it here rather than reinventing a rebuild-then-publish flow keeps that guarantee for the npm side too.

**Original plan (rejected on reflection, kept here for the record):** a fully separate `release-npm.yml` alongside `release.yml`. Wrong because it lets the two release pipelines drift independently — different tags, different timing, no guarantee a given VS Code extension version and a given npm-package version were ever actually tested or released together. The user's correction ("the release step should be shared so the same release includes all artifacts") is the right shape: there is exactly one release process for this project, producing four artifacts, not two disconnected release processes that happen to share a repo.
**Alternatives considered:** one combined workflow with a manual approval gate (GitHub Environments) instead of two publish files (`publish-marketplace.yml` + `publish-npm.yml`) — rejected for the same reason the existing split already stands: marketplace and npm are different destinations/credentials/audiences that may legitimately need independent timing (e.g. publish the extension now, hold the npm packages a day), so keeping them as two separately-triggerable, separately-confirmed workflows — both sourcing from the one shared release — gets both the shared-provenance guarantee and independent publish timing.

### 2. The Verdaccio smoke test becomes a step inside `release.yml`'s shared build job, not just a one-off manual check
**Decision:** a script (`scripts/test-npm-publish.sh` or similar, decided at implementation time), invoked as one of `release.yml`'s `build` job steps (see Decision 1) after the three packages are built and packed, that does exactly what this session did by hand: start `verdaccio` (already proven to work via `npx --yes verdaccio`) with a temp config scoping `@feimacode/*` to open publish, register a throwaway user via the registry's user-creation endpoint, `npm publish` all three packages to it in order, then in a separate temp directory with an isolated `.npmrc` pointing at the local registry, run `npx --yes @feimacode/open-design-agent-kit-mcp` and drive a real stdio JSON-RPC handshake (a Node script, adapted from this session's throwaway `handshake-test.mjs`), asserting `tools/list` returns 9 tools and a `tools/call` against `list_open_design_skills` returns real content. Also runs `npx --yes @feimacode/open-design-agent-kit init` against a fresh scratch dir and asserts the expected files exist. Non-zero exit (assertion failure, resolution failure, timeout) fails the CI job.
**Alternatives considered:** `npm pack --dry-run` + manual inspection only, without an actual local-registry round trip — rejected: this session's earlier `npm pack --dry-run` runs did NOT catch the cross-package dependency resolution question (whether `content` actually resolves as an installed dependency of `mcp-server`) at all — only the full publish-and-resolve cycle proved that, and that's exactly the class of bug (private, unpublishable transitive dependency) this whole gap-finding exercise started from.

### 3. Version pinning: a small pre-pack script in `release.yml`'s build job, not changesets
**Decision (sequencing corrected along with Decision 1):** since `publish-npm.yml` now only downloads and publishes the exact tarballs `release.yml` already built — it never rebuilds — the version-pinning rewrite must happen *before* `npm pack`, inside `release.yml`'s build job, not in `publish-npm.yml` (by the time `publish-npm.yml` runs, the tarball's contents are already fixed). The script rewrites `packages/mcp-server/package.json`'s `"@feimacode/open-design-agent-kit-content": "*"` to the exact version of `content` being released in that same run (e.g. `^0.1.0` or an exact pin — decide the range style at implementation time), in the CI checkout only, immediately before that package is packed — commits nothing itself, never touches the committed file — mirroring how many monorepo publish pipelines rewrite `"*"`/`"workspace:*"` ranges at pack/publish time without changing what's committed.
**Alternatives considered:** adopting `changesets` — genuinely the standard tool for exactly this problem (coordinated monorepo versioning + changelogs + publish orchestration), but rejected for this round specifically because this repo already has an established, working, fully-manual versioning convention for the VS Code side (`release.yml`'s explicit version-match check against `packages/vscode/package.json`, a hand-maintained `CHANGELOG.md`) — introducing changesets for only the npm side would mean two different versioning philosophies live side by side in one repo. Worth reconsidering later if the npm side's release cadence outgrows a single small rewrite script, but not the right scope for closing today's specific gap.

### 4. READMEs and `engines`
**Decision:** `packages/content/README.md` describes what it vendors and that it's regenerated by `npm run sync-content`, not hand-edited. `packages/cli/README.md` mirrors the root README's existing "Ways to use it" `npx @feimacode/open-design-agent-kit init` bullet, expanded with the `--tools` flag and what gets written per host. `engines.node` on all three: check this repo's actual minimum Node-version-sensitive API usage (e.g. `fs.cp`, added in Node 16.7+, already used in `skillWriter.ts`/`copy-skill-content.mjs`) before picking a number, rather than guessing a round value.
**Alternatives considered:** none of substance — these are straightforward completeness fixes with no real design tradeoff.

## Risks / Trade-offs

- **[Risk]** A CI-hosted Verdaccio instance behaves subtly differently from this session's manual local run (network/sandboxing differences in GitHub Actions runners). → **Mitigation**: the smoke-test script should be runnable identically both in CI and locally (no CI-specific branching), so a failure in CI can be reproduced and debugged on a developer machine the same way this session's manual run was built up.
- **[Trade-off]** The pre-publish version-rewrite script (Decision 3) means the version actually published can briefly differ from what's committed in git during the publish job — standard practice for this pattern, but worth documenting clearly in the workflow file itself so a future reader isn't confused about why the published `package.json` doesn't byte-for-byte match the repo.
- **[Risk]** `engines.node` is advisory only (npm warns, doesn't block, unless `engine-strict` is set) — won't by itself prevent a real user on an old Node version from hitting a confusing runtime error. → **Mitigation**: accepted as a documentation improvement, not a hard gate; revisit if this ever becomes a real support issue.

## Migration Plan

Additive; nothing existing changes behavior, and `release.yml`'s existing VS Code build/release path is unchanged apart from gaining sibling steps. Suggested build order (captured as tasks, not executed this round):
1. `engines`/README completeness fixes (small, no dependencies on anything else).
2. Version-pinning script and the Verdaccio smoke-test script, both tested locally by hand first (same method this session used) before wiring into CI.
3. Extend `release.yml`'s `build` job with the npm build/pack/version-pin/smoke-test steps, and its `release` job to attach the three `.tgz`s + checksums to the same GitHub Release as the `.vsix`.
4. `publish-npm.yml` (new, manual, confirmed, downloads from the shared release, real publish) — last, and not exercised for real until the user explicitly asks for an actual release.
