# Design: open-design-tools v1

## Interaction model: tools + instructions + prompts, no participant

Compared against a dedicated `@open-design` chat participant (mirroring `feima-copilot-llms-extension`'s `agents/claude/claudeParticipant.ts` pattern) and a tools-only minimal surface. Chosen: `languageModelTools` (the action layer, unavoidable regardless of choice) plus `chatInstructions` (steers Copilot's default agent toward the tools when relevant) plus `chatPromptFiles` (canned `/open-design-*` launchers). All three are confirmed-stable, non-proposed VS Code contribution points.

Why not a participant: it requires an explicit `@mention`, is its own conversational silo other agents can't reach into, and costs significantly more code (feima's `agents/claude/` subtree is ~15 files) for UX control this project doesn't need in v1. The user's own stated preference, twice independently (file-write mechanism and interaction model), was to lean on native VS Code/Copilot mechanisms over bespoke parallel machinery — see the project's assistant-memory record `feedback_native_over_bespoke`.

Why not custom chat modes: not extension-contributable (microsoft/vscode#251580 was open as of this research; workspace-file-only `.github/chatmodes/*.md`).

Why not an extension-managed MCP server: still the MCP transport, which is the thing this whole change exists to avoid — OpenDesign's own MCP server (`apps/daemon/src/mcp.ts`) was confirmed to be a pure HTTP proxy with zero embeddable logic; every tool call needs a live daemon. Reproducing that shape locally would just relocate the daemon dependency, not remove it.

## Why composeSystemPrompt() was not ported

`packages/contracts/src/prompts/system.ts` `composeSystemPrompt()` (~1180 lines) looked, from the outside, like exactly the reusable piece this project needed: a pure function assembling skill + design-system + craft + brief into one prompt. Reading it in full changed that assessment. It is tightly coupled to OpenDesign's own product surface:

- A `<question-form>` UI protocol only OD's own web/daemon client renders.
- `<od-card>` verify-scorecard / memory-applied tags tied to OD's personal-memory subsystem.
- An "OD Next" strategy-recipe fork (`odNextStrategyRecipe`).
- Deck-framework CLI dispatch referencing `$OD_NODE_BIN`/`$OD_BIN`.
- A media-generation contract dispatching through OD's own CLI.
- Explicit instructions to call `TodoWrite`, `Bash`, `Read`, `Write`, `Edit` — CLI-coding-agent tool names that don't exist in a VS Code Copilot Chat context.

Porting this verbatim would hand Copilot's model a prompt full of instructions describing tools and markup it cannot act on, which is worse than not having it — a model told to emit `<question-form>` or call `TodoWrite` when neither exists will either hallucinate the behavior or visibly fail.

Instead, `src/core/generation/composeInstructions.ts` is a new, minimal function written for this project's actual surface (native VS Code file-editing tools, no CLI, no daemon UI markup), reusing only the one clearly product-agnostic piece of the original — the "semantic output file names" guidance (don't default every artifact to `index.html`) — rewritten in its own words. See `src/core/vendored/SOURCE.md` for the full provenance breakdown.

## What was ported vs. rewritten vs. skipped

| Piece | Disposition | Why |
|---|---|---|
| `skills/*/SKILL.md`, `design-systems/*/DESIGN.md`, `craft/*.md` | Vendored verbatim (content, not code) | Plain markdown, no coupling |
| `apps/daemon/src/artifacts/manifest.ts` | Ported near-verbatim | Pure validation logic, zero daemon coupling |
| `apps/daemon/src/artifacts/create.ts` | Adapted | Injected `writeProjectFile` callback (for HTTP) replaced with direct `fs/promises` scoped to a workspace root — this extension has exactly one write target, so the abstraction the daemon needed doesn't apply here |
| `packages/contracts/src/prompts/system.ts` `composeSystemPrompt()` | Rewritten from scratch as `composeInstructions()` | See above |
| `apps/daemon/src/mcp.ts` (the MCP tool surface) | Reimplemented as native `languageModelTools`, not ported | Confirmed pure HTTP proxy, no logic to port; tool *shape* (list_skills, create_artifact, get_artifact) carried over conceptually |
| Daemon process/SQLite/subprocess-spawn machinery | Not used at all | Replaced entirely by Copilot's own model + native tool-calling as the "agent loop" |

## Artifact manifest compatibility

`register_open_design_artifact` writes the same `<entry>.artifact.json` sidecar shape OpenDesign's own daemon writes (via the ported `artifactManifest.ts`/`artifactCreate.ts`), so an artifact generated by this extension is structurally recognizable by an actual OpenDesign project if the user later imports the workspace folder there — this wasn't a hard requirement, but came for free from porting the validation logic closely rather than inventing a new shape.
