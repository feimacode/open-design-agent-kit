# Design: browse-vs-remix separation

## Why a separate preview panel instead of reusing ArtifactEditorProvider

`ArtifactEditorProvider` (`CustomTextEditorProvider`) is built around a real `vscode.TextDocument` — it needs an actual file on disk to back save/undo through `vscode.workspace.applyEdit`. Backing a preview with a virtual/untitled document was considered (a `TextDocumentContentProvider` on a custom URI scheme) but rejected as unnecessary complexity: examples are read-only by definition until remixed, so there's nothing to save/undo in a preview context, and Comment/Edit modes wouldn't have anywhere durable to persist to without misleading the user into thinking their in-preview edits mattered. A separate, deliberately simpler `ExamplePreviewProvider` — same singleton-`WebviewPanel` shape as `GalleryGridProvider`, no comment/edit machinery, no `CustomTextEditorProvider` document binding — is a cleaner fit: it exists purely to answer "what does this look like," with one explicit escape hatch (a Remix button) into the real, file-backed flow.

## Read-only guarantee

The panel's `loadExample()` only ever calls `fs.readFile` against paths under `this.assetsRoot` (this extension's own bundled `assets/open-design/examples/`) and never writes anything. The only file-system mutation reachable from this panel is the explicit "Remix into workspace" button, which goes through the same `remixAndOpen()`/`performRemix()` path as every other remix entry point — so "browsing never writes" is structural (the preview provider has no write path at all), not just a UI convention that could be bypassed by a different click target.

## Ready-handshake race, caught before it shipped

`GalleryGridProvider`/`ArtifactEditorProvider` both already establish content via a `ready` (webview → host) → `init`/`update` (host → webview) handshake, because posting a message before the webview's own script has loaded and attached its `message` listener silently drops that message — there's no queueing. The first draft of `ExamplePreviewProvider.show()` called `loadExample()` synchronously right after creating the panel, before the webview script could possibly have run yet. Caught during implementation (not by a test — there's no DOM harness for this) by re-checking against the established pattern already used elsewhere in this codebase; fixed by stashing the initial `skillId` and only loading it once the webview's own `ready` message arrives.

## QuickPick's asymmetry is intentional, not an oversight

The QuickPick (`OpenDesign: Browse Gallery`) still remixes immediately on selection, unlike the tree and grid. A QuickPick's `showQuickPick()` await resolves only on a committing selection (Enter, or click) — there's no distinct "just looking" gesture the way clicking a tree item or a grid card is (those are inherently "look at this" interactions in their respective UI idioms, VS Code's own tree/list views everywhere use single-click-to-select-and-preview as a baseline convention). Changing the QuickPick to a two-step browse-then-confirm flow would add friction to what's supposed to be the fastest, most keyboard-driven of the four entry points, and wasn't what was reported as broken.

## TypeScript module-scope gotcha (real bug, not hypothetical)

`tsc -p src/webview` type-checks all matched files as one project. A `.ts` file with no `import`/`export` of its own is treated by TypeScript as a global script, not an ES module — its top-level declarations live in one shared global scope across every such file in the compilation, not a per-file scope. `src/webview/gallery/main.ts` and the new `src/webview/preview/main.ts` both declared top-level `const vscode = acquireVsCodeApi()` and `const root = ...` with no local imports of their own, so adding the third entry point immediately surfaced `TS2451: Cannot redeclare block-scoped variable` between them (and would have between any two files in this shape). Fixed with an explicit `export {};` at the top of each such file, forcing module scope. `src/webview/main.ts` never hit this because it already imports from `./dom/elementTargeting` etc., which is enough to make TypeScript treat it as a module — worth remembering for any future webview entry point that happens to be self-contained (no local imports): it needs the same `export {};` line, not just "add another entry to `.esbuild.ts`."
