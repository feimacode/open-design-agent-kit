# Design: import design system

## Why deterministic, not model-authored, for this path

The prior round's `create_open_design_design_system` is deliberately model-authored — right for inventing a look from a loose brief, where judgment about what looks coherent matters. Importing an org's *actual* design system is a different problem: the values need to be exact, not reinterpreted. Handing pasted tokens to the model as "brief text" risks it paraphrasing a hex code, dropping a font, or otherwise treating precise data as loose inspiration. This path never touches the model — `buildDesignSystemMarkdown()` either passes content through verbatim (already-shaped) or extracts + wraps it with the original always preserved verbatim, so nothing regex-extraction misses is ever silently lost either.

## Why `DESIGN.md` takes priority and is used alone for a bare GitHub repo

If a repository already has a `DESIGN.md` (the exact shape this catalog wants), concatenating it with other found token files (a Tailwind config, a tokens.json) before extraction would be actively harmful — `looksLikeDesignMd()` would see the concatenated blob's first line (whichever file happened to be probed first) and might not recognize it as already-shaped, causing a perfectly good hand-written `DESIGN.md` to get wrapped and diluted with a "Color Palette" section generated by regex-scanning the *rest* of the concatenated text. Checking for `DESIGN.md` first and returning early avoids this altogether: if it's there, that's obviously the intended source.

## The `kind` field collision (caught by `tsc`, not by runtime testing)

The first draft of the source-type QuickPick item used `interface SourcePickItem extends vscode.QuickPickItem { kind: SourceKind }` — but `vscode.QuickPickItem` already declares its own `kind?: QuickPickItemKind` (used to mark an item as a non-selectable separator, the same mechanism `browseDesignSystemsCommand.ts` already uses for category separators). TypeScript correctly rejected the interface extension (`'file'` isn't assignable to `QuickPickItemKind`), caught immediately by `npm run typecheck`, before any runtime test could have surfaced it. Renamed the custom field to `sourceKind` to avoid the collision — worth remembering for any future QuickPick item shape: `kind` is a reserved name on the base interface, not a free field name.

## Why `fs/promises` instead of `vscode.workspace.applyEdit` for the write

Every other file write that goes through the *model* in this extension happens via the model's own native editing tools (which use `WorkspaceEdit`/`applyEdit` under the hood, giving free undo). This command's write isn't mediated by the model at all — there's no existing `TextDocument` open for a WorkspaceEdit to apply against (it's a brand-new file), so it writes directly with `fs.mkdir`/`fs.writeFile`, matching how `artifactComments.ts` and the vendored `artifactCreate.ts` already write other workspace-local sidecar files outside the model-edit path. The result is opened via `vscode.window.showTextDocument` immediately after, so the user still sees and can review/undo-from-there via the normal editor, just without a WorkspaceEdit history entry for the initial write itself (consistent with how remix's initial file copy also isn't a WorkspaceEdit — only a model's own subsequent edits are).

## GitHub: no auth in this round

Unauthenticated GitHub API/raw-content requests are rate-limited (60/hour for the `api.github.com` metadata call) and can't reach private repositories at all. Both are real, known limitations, not oversights — deferred to a later round (per the user's own staging choice) since supporting them needs `context.secrets`-backed personal-access-token storage, the same credential-management work Figma import would also need. Building that infrastructure once, for both, is better than building it twice.
