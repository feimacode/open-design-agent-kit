## Context

OpenSpec's own `init` command (`~/toys/OpenSpec/src/core/init.ts`, `src/cli/index.ts`, `src/core/config.ts`, read directly this session, not from memory) is the concrete reference: a `commander`-based CLI (`bin: { openspec: ... }`) with an `AI_TOOLS` registry (~28 entries, each a `{ name, value, skillsDir }`), an interactive multi-select prompt with a `--tools <list|all|none>` non-interactive escape hatch, and a `CommandAdapterRegistry` that renders one logical command set into each tool's own format/location. `init [path]` (default `.`) writes directly into the *caller's* project — `<path>/<tool.skillsDir>/skills/<name>/SKILL.md` — with no marketplace, no install step, nothing beyond running the command.

This repo already has the two ingredients an equivalent command needs: `packages/claude-plugin/skills/` (overview + 23 curated skills, Claude-Skill-shaped) and the repo-root `.agents/skills/` (the same content, Codex-shaped, plus `agents/openai.yaml` sidecars), both regenerated by `npm run sync-content` from `packages/content/scripts/curatedEntries.mjs`. Both are currently reachable only via a Claude Code plugin marketplace add, or a manual copy out of a clone of this repo.

## Goals / Non-Goals

**Goals:**
- Give a user a one-command (`npx @feimacode/open-design-agent-kit init`) way to get OpenDesign's Claude Code and/or Codex integration set up directly in their own project, matching the ergonomics of `npx openspec init`.
- Reuse this repo's already-generated skill content as the source of truth — `init` never independently re-derives or duplicates what `packages/claude-plugin`/`packages/codex` already produce.
- Make `init` safe to re-run: it should never destroy content it doesn't own (a user's other MCP servers in `.mcp.json`, an existing hand-written `.codex/config.toml`).

**Non-Goals:**
- Matching OpenSpec's full ~28-tool `AI_TOOLS` matrix. Scoped to Claude Code + Codex only this round (explicit user decision) — most of the other 26 tools only understand MCP with no bespoke skill-file convention of their own, so this is additive scope later, not a rework.
- Replacing the Claude Code plugin marketplace path (`packages/claude-plugin` + the root `.claude-plugin/marketplace.json`). `init` is a second, faster, no-marketplace option for the same two hosts, not a deprecation of the first.
- A comment-preserving TOML round-trip. See Decision 3 — deliberately avoided by never rewriting an existing `.codex/config.toml`, rather than solving round-trip fidelity.
- Auto-detecting which tools are already configured in the target project (OpenSpec's `getAvailableTools`/pre-selection logic) — with only two choices, a plain checkbox with both pre-selected is enough; detection-based pre-selection is a nice-to-have for a future round if the tool list grows.

## Decisions

### 1. A new, separate package (`packages/cli`), not folded into `packages/mcp-server`
**Decision:** `packages/cli`, published as `@feimacode/open-design-agent-kit`, with its own `bin`. Kept separate from `packages/mcp-server`'s existing `bin` (`open-design-mcp`).
**Alternatives considered:** adding `init` as a subcommand on the mcp-server binary (`open-design-mcp init`) — rejected: an MCP host's `.mcp.json`/`config.toml` entry invokes that binary expecting it to immediately speak MCP over stdio with no argument parsing; overloading it with subcommands risks a host accidentally invoking the wrong mode, and conflates "the thing a host process runs" with "the thing a human runs once at setup time" — two different lifecycles that OpenSpec itself also keeps as one CLI but clearly distinct from anything an agent host directly execs (OpenSpec has no MCP-server mode at all, so this distinction didn't need solving there — worth calling out as a difference from the reference, not an oversight).

### 2. `.mcp.json` merge is a safe, direct read-parse-merge-write (JSON has no comment-loss risk)
**Decision:** read the target project's `.mcp.json` if it exists (`JSON.parse`), set `mcpServers.open-design` to the standard `{ command: "npx", args: ["-y", "@feimacode/open-design-agent-kit-mcp"] }` entry, leave every other key untouched, `JSON.stringify(..., null, 2)` back. If the file doesn't exist, create it with just that one entry.
**Alternatives considered:** text-based surgical insertion (regex/string splice) instead of a real parse — rejected as strictly worse here: JSON has no comments or meaningful whitespace to preserve, so a real parse+merge is both simpler and safer than ad hoc text manipulation, with zero fidelity trade-off.

### 3. `.codex/config.toml` is only ever written when it doesn't already exist; an existing file is never rewritten
**Decision:** check for the file's existence first. If absent, write a fresh one containing just `[mcp_servers.open-design]`. If present, parse it read-only (a lightweight TOML parser, evaluated but not for writing — see below) only to check whether an `open-design` entry already exists, and print the exact snippet to add by hand either way, rather than attempting to merge and rewrite the file.
**Why, and alternatives considered:** TOML, unlike JSON, commonly carries comments and hand-tuned formatting; every JS TOML library surveyed (`@iarna/toml`, `smol-toml`, `@ltd/j-toml`) parses to a plain data structure and re-serializes from that structure on write, which is not guaranteed to preserve a user's original comments/formatting/key order. Rewriting a file the user may have hand-curated, with a real risk of silently reformatting or dropping something, fails this project's own standing bar for care around already-existing content (the same bar `packages/content`'s "vendor, don't clobber" conventions and the earlier `ActiveDesignSystemStore`/mirror work were built to). Only ever writing a *brand-new* file (nothing to lose) while printing instructions for the *existing-file* case avoids the whole fidelity question rather than picking a library and hoping. A lightweight parser (`smol-toml`, spec-compliant TOML 1.0, no native deps) is still worth adding for the read-only existence check, so the printed guidance can say "already registered" vs. "add this" accurately instead of always printing the snippet unconditionally.

### 4. Skill files are always fully regenerated on `init`; config files only ever have their own entry touched
**Decision:** `.claude/skills/*` and `.agents/skills/*` in the target project are pure generated content — `init` always overwrites them wholesale from this package's bundled copy (no partial merge logic needed, matching how `generate-claude-skills.mjs`/`generate-codex-skills.mjs` already treat their own generated directories in this repo). `.mcp.json` and `.codex/config.toml` are the opposite case — files the user's own project owns, where `init` must touch only its own entry (JSON) or nothing at all if it can't do so safely (TOML, per Decision 3).
**Alternatives considered:** marker-based selective cleanup for skill files, mirroring `generate-claude-skills.mjs`'s own `isGeneratedSkillDir` safety check (never delete a directory lacking the generated marker) — worth carrying over as the SAME safety property here (don't delete a `.claude/skills/<id>/` directory a user created themselves that happens not to be one of ours), even though full regeneration of OUR OWN directories needs no merge logic.

## Risks / Trade-offs

- **[Risk]** A target project's `.mcp.json` is malformed/non-JSON. → **Mitigation**: fail clearly with the parse error and the file path, don't silently overwrite; never guess at partial recovery.
- **[Risk]** Bundling the skill content inside the published `@feimacode/open-design-agent-kit` package means it can drift from `packages/claude-plugin`'s/`packages/codex`'s own copies if `init` isn't re-published alongside a content sync. → **Mitigation**: `packages/cli` reads its bundled content the same way `packages/mcp-server` reads `packages/content` — from a real npm dependency (`@feimacode/open-design-agent-kit-content` or directly vendoring the generated `packages/claude-plugin/skills/`/`.agents/skills/` output at publish time) rather than a second, independent generation path; a drift-guard analogous to the existing three (`check-content-sync`, `check-content-mirror`, `check-skills-sync`, `check-codex-skills-sync`) should cover this too.
- **[Trade-off]** Not attempting a comment-preserving TOML round-trip (Decision 3) means a user with an existing `.codex/config.toml` gets a print-and-copy step instead of full automation — a real ergonomics cost, accepted deliberately over the alternative risk of corrupting a file `init` didn't create.

## Migration Plan

Additive; nothing existing changes behavior. Suggested build order (captured as tasks, not executed this round):
1. `packages/cli` scaffold + `init` argument parsing + interactive/non-interactive tool selection.
2. Claude Code path: skill copy + `.mcp.json` merge.
3. Codex path: skill copy + conditional `.codex/config.toml` write/print.
4. Manual verification: run `init` against a real scratch project for both tools, confirm Claude Code and Codex actually pick up the result in a live session (same category of gap as `agent-plugin-support`'s tasks 5.6/6.4 — tracked honestly if not achievable in an automated environment).

## Open Questions (resolved during implementation)

- Bundled-content strategy: resolved as vendoring — `packages/cli` mechanically mirrors `packages/claude-plugin/skills/` and `.agents/skills/` into its own `assets/` at build time (`copy-skill-content.mjs` + `check-cli-assets-sync.mjs`), confirming the anticipated answer. `packages/core`/`packages/content` turned out to be unreferenced by `packages/cli` at all, which also resolved Decision "1.3 esbuild" below as unnecessary — see tasks.md 1.3.
- `--yes`/default-both-tools shortcut: not built. `--tools all` already covers the CI/scripted case; a separate `--yes` flag would be a redundant second spelling of the same thing.
