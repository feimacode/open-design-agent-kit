- [x] 8.3 **Real, pre-existing bug found while checking bare-id uniqueness for 8.2, fixed after explicit user approval**: `ContentIndex`'s internal catalog (`packages/core/src/content/contentIndex.ts`) merged `skills/`, `design-templates/`, and `examples/` into one `Map` keyed by bare directory name. 129 of 444 real vendored entries share a bare id across pools (an 'example' is typically the rendered counterpart of a same-named skill/template, by design) — and critically, all 129 pairs also share the same computed `mode`, so the public `od:<mode>:<dirId>` id didn't disambiguate them either. The old `new Map([...skills, ...templates, ...examples])` merge silently kept only the last-spread (`example`) entry for every such pair: 25 of 163 skills and 104 of 114 design-templates were unreachable under their own identity, `list_open_design_skills` returned 315 entries instead of 444. Pre-existing, not introduced this session — affects the already-shipped VS Code extension identically to the new MCP server, since both share `ContentIndex`. Fixed with `mergeSkillPools()`: within a colliding group, the highest-priority source (skill > design-template > example) keeps the plain id; every other member gets its own source name appended (`od:<mode>:<dirId>:example`) — so none of the previously-correct ~315 ids change, and the previously-shadowed 129 become reachable under a clearly-labeled id instead of vanishing. `getSkill()` updated to try an exact (now collision-safe) id match first, falling back to a bare-dirId search with the same source-priority tie-break for legacy/ambiguous lookups. 4 new unit tests reproducing the exact collision shape (a skill and a same-mode same-named example) — verified against the REAL vendored catalog too, not just the fixture: `listSkills()` now returns exactly 444 (163+114+167), matching the sync counts precisely. Full check suite (typecheck × 4, lint × 4 incl. all four drift guards, 93+10 unit tests, both compiles) re-run clean after the fix.
