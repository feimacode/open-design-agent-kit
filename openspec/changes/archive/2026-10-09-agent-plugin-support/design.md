## Context

OpenDesign's logic already splits cleanly into `packages/core` (vscode-free: `ContentIndex`, `composeInstructions`, brand/token/design-system extraction and import, artifact manifest/create, and three vscode-free workspace helpers) and `packages/vscode` (the only consumer today, wrapping core as native `languageModelTools` + `chatInstructions` + `chatPromptFiles` + VS-Code-only webview UI for live preview/comments/WYSIWYG editing). That split was made specifically so a second, non-VS-Code consumer could be added later without reshuffling the vscode-coupled and vscode-free code apart from scratch. This design is that next step.

Two vscode-coupled pieces have no portable sibling yet:
- `activeDesignSystem.ts` — persists the active design system id via `vscode.workspace.getConfiguration`.
- `artifactWriter.ts` — writes files via `vscode.workspace.fs`; `remixOrchestrator.ts` is transitively coupled through it.

Vendored content (~15MB: skills, design-templates, design systems, craft, examples, synced from the public `nexu-io/open-design` repo pinned to a release tag) lives under `packages/vscode/assets/open-design/`, produced by `packages/vscode/scripts/{sync-open-design-content,check-content-sync,generate-featured-prompts}.mjs`. A prior round deliberately left this under `packages/vscode` rather than `packages/core`, flagging cross-package content sharing as "real scope for when the second package actually exists."

The target hosts — Claude Code and Codex — are both CLI/IDE-integrated coding agents that speak MCP (Model Context Protocol) for external tools, but differ sharply in how much else they offer: Claude Code has a native plugin system (bundlable Skills, slash Commands, subagents, hooks, and MCP server registration, distributed via a marketplace manifest); Codex, as far as this session's knowledge goes, offers MCP server registration and an `AGENTS.md`-based instructions convention, but no equivalent plugin/marketplace/skill-bundling system. That gap should be re-verified against Codex's current docs at implementation time rather than assumed to still hold.

## Goals / Non-Goals

**Goals:**
- Give any MCP-capable coding agent (Claude Code, Codex, and others not named explicitly) the same tool surface VS Code Copilot Chat already has: browse skills/design-systems, prepare a brief, register/read back an artifact, manage the active design system, create/import a design system, port an artifact to app code, remix an example.
- Give Claude Code specifically a first-class, one-command-installable plugin (skill doc + curated slash commands + the MCP server), matching the polish of the existing VS Code integration rather than just exposing raw MCP tools with no guidance.
- Establish one home for vendored content so a third host package never has to choose between duplicating it or reaching into `packages/vscode`.
- Keep the VS Code integration's own architecture and its "no daemon, no MCP transport" decision completely unchanged — this is an additive path, not a migration.

**Non-Goals:**
- Porting live preview, pinned comments, or WYSIWYG editing to any non-VS-Code host. These are inherently webview-UI features; a CLI agent has no equivalent surface to render them in. Hosts without a preview UI simply get a tool response that doesn't assume one exists.
- Building or wiring an actual Codex plugin/skill system that may not exist — the Codex section of this plan is intentionally scoped to what's verifiably available (MCP registration, AGENTS.md) plus a flag to re-check before building more.
- Auto-editing any user's global agent configuration (`~/.codex/config.toml`, Claude Code's own settings) on their behalf. All registration steps are either a one-time manual config snippet the user copies in, or (for Claude Code) the plugin's own install flow.
- Publishing to npm / a Claude Code marketplace as part of this change. This plan defines the shape; publishing is a separate, later, explicitly-approved step.

## Decisions

### 1. Extract vendored content into `packages/content`
**Decision:** new package `packages/content` (no build step, just data + the two host-agnostic sync/check-drift scripts moved from `packages/vscode/scripts/`), holding `assets/open-design/` and `MANIFEST.json` as the single real vendoring target synced from upstream. `packages/core`'s `ContentIndex` already takes a root path.
**Implementation-time refinement (found while building, not anticipated here):** a packaged VS Code extension (`.vsix`) must contain its content physically inside its own installed directory — `context.extensionUri` cannot resolve into a sibling npm workspace package, and `.vscodeignore` excludes `node_modules/**` from the package entirely (the esbuild bundle inlines all JS dependencies, so nothing there needs to ship as real files — but static data assets aren't part of that bundle). So `packages/vscode` keeps `assets/open-design/` as a *mirrored copy*, produced by a small `copy-content-assets.mjs` step that runs as part of `sync-content` right after `packages/content`'s own sync, with its own drift guard (`check-content-mirror.mjs`, wired into `lint`) comparing the mirror's `MANIFEST.json` against the canonical one. `packages/mcp-server`, having no such packaging constraint (published as a plain npm package, not bundled into a single-file VSIX), reads `packages/content`'s assets directly with no mirror needed. This keeps exactly one real *sync-from-upstream* step and prevents the two-independent-syncs drift the twenty-eighth round originally flagged; it does not achieve literal zero-copy-of-content-anywhere, which turned out to be incompatible with how VS Code packages extensions.
**Alternatives considered:** (a) leave content under `packages/vscode` and have `packages/mcp-server` reach into it via a relative path across package boundaries — rejected, it inverts the dependency direction (a "vscode" package becoming a runtime dependency of a non-vscode package) and breaks if `packages/vscode` is ever excluded from a publish. (b) duplicate the sync-from-upstream step per package — rejected outright, guaranteed drift, and this is exactly the risk the twenty-eighth round flagged and deferred. (c) have `packages/vscode` symlink or `require.resolve` its way into `packages/content`'s assets at runtime instead of mirroring — rejected once the `.vscodeignore`/`node_modules` packaging constraint above was confirmed; would silently ship a content-less extension.

### 2. `ActiveDesignSystemStore` as a core-level interface
**Decision:** add to `packages/core`: `interface ActiveDesignSystemStore { get(): Promise<string | undefined>; set(id: string | undefined): Promise<void>; }`. `prepare_open_design_brief` and `set_active_design_system`'s shared logic (currently free-floating in `packages/vscode`) takes this as a dependency instead of assuming `vscode.workspace.getConfiguration`. `packages/vscode`'s `activeDesignSystem.ts` becomes an implementation of this interface (no behavior change for VS Code users). `packages/mcp-server` gets a new plain-JSON-file implementation, `.open-design/config.json` relative to the server's working root (see Decision 4).
**Alternatives considered:** duplicating the "resolve explicit-or-active, fall back gracefully on a stale id" logic per host — rejected, that logic (not just storage) is exactly the kind of behavior this project already treats as core, and duplicating it risks the two hosts silently drifting in edge-case behavior (e.g. the "stale active id degrades gracefully" scenario in the existing spec).

### 3. `packages/mcp-server`: one MCP server, same tool contract as VS Code
**Decision:** new package `@feimacode/open-design-agent-kit-mcp`, a stdio MCP server (`@modelcontextprotocol/sdk`, the standard/official SDK — not a bespoke JSON-RPC implementation) with a `bin` entry so it runs via `npx @feimacode/open-design-agent-kit-mcp` with no local checkout. It registers the same nine tools, same names, same input/output JSON shapes as today's VS Code `languageModelTools`, so a single instructions document (Decision 5) can describe the flow identically regardless of host. One host-specific piece is supplied at startup: the `ActiveDesignSystemStore` (Decision 2), file-backed at `.open-design/config.json`. The workspace root defaults to `process.cwd()` (matching how both Claude Code and Codex launch local stdio MCP servers with the session's working directory), overridable via an `OPEN_DESIGN_WORKSPACE_ROOT` env var for testing. Tool responses that, on VS Code, describe an auto-opened preview editor instead state the file was written and where, with no preview-related instruction.
**Alternatives considered:** a per-host binary with divergent tool names — rejected, it would fork the instructions doc and the "how to use OpenDesign" mental model per host, undermining the whole point of a shared MCP layer. An HTTP/SSE transport instead of stdio — rejected for v1; stdio is the zero-config default both target hosts support for a locally-run server, and there's no multi-client/remote-hosting requirement yet.
**Correction (found during implementation): no `writeProjectFile` injectable callback exists or is needed.** This decision (and the original proposal) assumed `artifactCreate` needed an injected file-write callback, based on a stale memory of the upstream daemon's design. The actual current code already dropped that indirection: `writeArtifactManifest`, `readArtifact`, and `copyExampleArtifact` all do plain `fs/promises` I/O scoped to a `workspaceRoot: string` parameter. `packages/mcp-server` calls these directly — nothing to inject.
**Addendum: `McpServer.registerTool()` (the SDK's high-level, zod-based API) is unusable here — it OOM-crashes `tsc`.** Registering all nine tools through `registerTool`'s generic, zod-raw-shape-based overload caused `tsc` to grow past several GB of heap and crash, even under `--max-old-space-size=4096` — a reproducible TS generic-inference blowup from that signature's overload complexity combined with the SDK's zod v3/v4 compatibility layer, not a bug in this package's own code. Fixed by using the SDK's lower-level `Server` class directly (`setRequestHandler(ListToolsRequestSchema, ...)` and `setRequestHandler(CallToolRequestSchema, ...)`, dispatching by tool name) with plain, hand-written JSON Schema objects for each tool's `inputSchema` — mirrored 1:1 from `packages/vscode/package.json`'s existing `contributes.languageModelTools` schemas, so the two hosts' tool contracts stay identical by construction. This dropped typecheck time from an OOM crash to ~2 seconds. Worth flagging for anyone extending this package: prefer the low-level `Server` API over `McpServer.registerTool` in this codebase until the SDK's overload performance improves upstream.
**Addendum: `packages/core` has no runtime-resolvable compiled output — `packages/mcp-server` needs its own esbuild bundle, the same way `packages/vscode` does.** `packages/core/package.json`'s `main`/`types` point at raw `src/index.ts`; this works for `packages/vscode` only because esbuild bundles TypeScript source directly and never goes through Node's own `require()` resolution. The first attempt to run `packages/mcp-server` — both its unit tests and the real compiled server — failed with `ERR_MODULE_NOT_FOUND` trying to `require()` a `.ts` file. Rather than giving `packages/core` a second, parallel compiled-output convention that `packages/vscode` doesn't use (a real cross-package compatibility risk), `packages/mcp-server` gets its own `.esbuild.ts`, inlining `@feimacode/open-design-agent-kit-core`'s source the same way `packages/vscode` already does — and its own dependency, `@modelcontextprotocol/sdk`, is genuinely a normal npm package with no such problem, so it's left external rather than bundled. `@feimacode/open-design-agent-kit-content` is also left external deliberately: it's ~15MB of data, not code, resolved at runtime via `require.resolve` against a real installed `node_modules` entry — bundling would defeat that. Unit tests run via `mocha --require tsx/cjs` directly against `.ts` sources (both the package's own and, transitively, `packages/core`'s), avoiding a separate compile-then-run step entirely for tests.

### 4. `packages/claude-plugin`: plugin bundle + marketplace, not a duplicate skill catalog
**Decision:** new `packages/claude-plugin/` containing `.claude-plugin/plugin.json` (name, description, version, author), a sibling `.mcp.json` (the current, correct location for MCP server registration — see the implementation-time correction below) pointing at `packages/mcp-server` via `npx`, `skills/open-design/SKILL.md` (a Claude-Skill-frontmatter port — `name`/`description` tuned for Claude Code's own auto-trigger matching — of today's single `open-design.instructions.md`, referencing the MCP tool names as Claude Code will expose them), and one generated `skills/<id>/SKILL.md` per curated entry (`disable-model-invocation: true`, invoked explicitly as `/open-design:<id>` — see the correction below for why this is a skill, not a `commands/*.md` file). A root-level `.claude-plugin/marketplace.json` lists this one plugin so `/plugin marketplace add <this-repo>` then `/plugin install open-design` works directly against the repo, no separate marketplace repo needed. **Deliberately still one *overview* skill document, not 277 individual Claude Skills** (one per vendored OD skill/design-template) — the curated 23 do become individual (cheap, explicit-only) skills, but the long tail stays behind the `list_open_design_skills` MCP tool, same shape as the VS Code integration's curated-`chatPromptFiles`-vs-long-tail split.
**Correction (verified against Claude Code's current docs, task 5.1, before writing any file):** two assumptions in the original proposal were wrong. (1) MCP servers are declared in a separate `.mcp.json` file at the plugin root, not a `mcpServers` field inside `plugin.json` (that field exists too, but only to point at a non-default path or supply an inline override). (2) Flat `commands/*.md` files are explicitly documented as the *legacy* format for new plugins — current guidance is `skills/<name>/SKILL.md`, with `disable-model-invocation: true` producing exactly the old "explicit-only shortcut" behavior a `commands/` file gave. Both corrected throughout this document and the task list.
**Alternatives considered:** mapping each curated/featured OD skill to its own Claude Skill (closer to 1:1 fidelity with "OpenDesign has a skill called X") — this is in fact what the corrected design now does for the 23 curated entries, since a Claude Skill's always-on cost is just its `name`+`description` line (loaded lazily in full only on invocation) rather than a full schema sent every turn — a materially different cost model than VS Code's `languageModelTools`, so the original VS Code-derived "avoid N-per-entity" argument didn't actually transfer here for the *curated* subset. It still holds for the full ~280-entry catalog, which stays behind the MCP list tool rather than becoming 280 skills.

### 5. Shared command/prompt generator
**Decision:** the curated-entry detection logic (presence of `featured`/`recommended`/`od.default_for` in vendored frontmatter) that today only emits VS Code `chatPromptFiles`, moves into `packages/content`'s generation scripts (`curatedEntries.mjs`, done) and gains a second emitter for Claude Code's `skills/<id>/SKILL.md` shape, run from the same `npm run sync-content` pass that already regenerates the VS Code prompts. One source of "which entries are curated," two output shapes.
**Alternatives considered:** a second, independently-maintained generator script living in `packages/claude-plugin` — rejected, this is precisely the "two things that must stay in sync but don't have to" hazard the thirtieth round's `check-content-sync.mjs` guardrail already exists to prevent for the vscode side; better to never let it fork in the first place.

### 6. Codex: MCP registration + skill file, documented not automated
**Original decision (superseded — see correction below):** document, not automate: an `~/.codex/config.toml` snippet registering `packages/mcp-server`, and an optional AGENTS.md instructions fragment the user pastes into their project's `AGENTS.md`, since Codex's extensibility surface beyond MCP registration was not confirmed to exist at proposal time.
**Correction (verified during implementation, task 6.1 — this plan's own "re-verify before building more" instruction paid off):** Codex's extensibility surface turned out richer than assumed. It has (a) genuine MCP support, TOML-configured (`[mcp_servers.<name>]` in `~/.codex/config.toml` or a project-scoped `.codex/config.toml` — a different syntax family from Claude Code's `.mcp.json`, both documented in `docs/codex.md`), and (b) its own Skills system with a `SKILL.md` format shaped like Claude Code's (`name`+`description` frontmatter), discovered from `.agents/skills/<name>/SKILL.md` at repo root/cwd/user-home. Given (b), copying `packages/claude-plugin/skills/open-design/SKILL.md` into a project's `.agents/skills/open-design/SKILL.md` is a better, more targeted mechanism than a parallel AGENTS.md fragment (which would duplicate the same guidance as an always-on repo instruction instead of a model-matched skill) — so the AGENTS.md fragment was dropped as redundant, not built. Both the MCP registration and the skill-copy are pure documentation (`docs/codex.md`); nothing in `packages/mcp-server` needed to change for either. Still correctly out of scope: Codex/ChatGPT's shared "universal plugin directory," which requires submitting through OpenAI's own distribution process — a heavier, account-level mechanism genuinely outside what this repo can wire up unilaterally, not merely deferred out of caution this time.
**Alternatives considered:** a CLI helper that edits `~/.codex/config.toml` automatically — rejected per this project's standing principle of not silently touching state outside the workspace/repo it's asked to operate in, and per this design's explicit non-goal of auto-editing global agent config.

## Risks / Trade-offs

- **[Risk]** Claude Code's plugin manifest schema (`plugin.json`/`marketplace.json` field names) may differ in detail from what's assumed here, since it's a newer, evolving surface. → **Mitigation**: treat the exact manifest shape as an implementation-time detail to verify against Claude Code's own current plugin docs (or by asking a `claude-code-guide` agent) before writing `plugin.json`, not something to lock down further in this design doc.
- **[Risk]** Assuming both Claude Code and Codex launch local stdio MCP servers with `cwd` set to the active project — if either instead uses a different working directory convention, the default-root behavior in Decision 3 silently targets the wrong folder. → **Mitigation**: the `OPEN_DESIGN_WORKSPACE_ROOT` override exists specifically for this; verify the actual default behavior for each host during implementation, in a real session, before shipping.
- **[Risk]** Duplicating tool response wording (preview-editor-specific language for VS Code vs. plain file-location language for MCP hosts) could drift the two prompt surfaces apart over time. → **Mitigation**: keep the divergence to the smallest possible slice (one templated sentence per relevant tool), not a full fork of `composeInstructions()` or the tool handler bodies.
- **[Trade-off]** Choosing one shared skill/instructions document (Decision 4) over host-native per-skill mapping trades some "feels native to Claude Code" polish for consistency and the already-validated cost argument against N-per-entity registration.
- **[Risk]** The Codex section may end up mostly wrong if Codex's extensibility model has moved on since this session's cutoff. → **Mitigation**: explicitly flagged provisional in both this design and the spec delta; the concrete, low-risk MCP-registration doc still stands on its own regardless of what else Codex has added.

## Migration Plan

This is additive; nothing existing is removed or must be rolled back. Suggested build order (captured as tasks, not executed this round):
1. `packages/content` extraction (mechanical move + repoint `ContentIndex` callers) — verify `packages/vscode` still passes its full check suite unchanged.
2. `ActiveDesignSystemStore` interface + vscode implementation refactor — verify no VS Code behavior change.
3. `packages/mcp-server` — build against a real MCP client (e.g. the MCP inspector, or a manual Claude Code session) end-to-end before considering it done, not just unit tests of the underlying core calls.
4. `packages/claude-plugin` — manual verification via an actual `/plugin install` in a real Claude Code session, mirroring how the VS Code extension's own manual-verification gap is tracked honestly rather than assumed passing.
5. Codex documentation snippet — manual verification in an actual Codex session once step 3 exists, since Codex needs nothing new built, only the existing MCP server registered.
